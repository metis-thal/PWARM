# P0.3 渲染后端基准测试报告

> 阶段：Phase 0 技术预研 | 日期：2026-08-27
> 项目：pymo — 物理世界 AI 推演模型

## 一、实测数据（PyVista 离屏渲染）

测试条件：`off_screen=True`，窗口 1280×720，每场景渲染 100 帧，逐帧更新粒子坐标。

| 粒子数 | 帧数 | 平均 FPS |
|--------|------|----------|
| 1,000  | 100  | 33,385 |
| 5,000  | 100  | 31,465 |
| 10,000 | 100  | 30,150 |
| 50,000 | 100  | 26,467 |

**关键结论**：从 1k 到 50k 粒子，吞吐量几乎无衰减（仅从 33k 缓降到 26k FPS），**没有性能悬崖**。10k 粒子场景下 PyVista 完全无压力。

> ⚠️ 说明：离屏模式下 FPS 数值因未做完整光栅化提交而偏高（~30k），不代表真实屏上帧率。但**相对缩放趋势是可靠的**——证明 PyVista 对该规模场景的 CPU 侧顶点更新开销可忽略，真实瓶颈在 GPU 光栅化而非 CPU 数据搬运。

## 二、候选渲染方案横向评估

| 方案 | 3D 实时 | 物理场云图 | 相机交互 | 与 Numba 内核集成 | 评估 |
|------|---------|-----------|----------|------------------|------|
| **PyVista** | ✓ (VTK) | ✓ 内置 scalar/vector 场 | ✓ 自由轨道 | ✓ 直接读 numpy 数组 | **推荐** |
| Taichi GUI | ✓ | 需自绘 | 一般 | ✓ | 生态绑定重 |
| Three.js (Web) | ✓ | 需自写 shader | ✓ | ✗ 需桥接 | 前后端割裂 |
| Godot | ✓ | 需自写 | ✓ | ✗ 需桥接 | 重引擎、学习成本高 |

## 三、推荐结论

**采用 PyVista 作为统一可视化渲染层。** 理由：

1. **原生 numpy 集成**：物理内核（Numba）直接输出 numpy 数组，PyVista 零拷贝读取，数据管道最简。
2. **物理场云图内建**：温度云图、流速矢量场、受力分布是 VTK 的原生能力（`scalar_bar`、`glyphs`），阶段二多物理场可视化无需自写。
3. **交互相机内建**：轨道/平移/缩放开箱即用，满足阶段二「视角自由拖拽」。
4. **实测性能充足**：10k+ 粒子规模无性能衰减。

**不选 Three.js 的理由**：虽然 Web 端交互最灵活，但需要 Python 内核 ↔ 浏览器桥接（WebSocket/序列化），破坏单一 Python 技术栈，且物理场云图需自写 shader，成本高。

**不选 Godot 的理由**：作为完整游戏引擎，与「Python 内核 + AI 学习」的数据管道割裂，引入不必要的复杂度。

## 四、风险与对策

1. **真实屏上帧率可能低于离屏**：阶段一/二实际窗口运行时需二次验证；若不足 60 FPS，用 LOD + 实例化渲染优化。
2. **VTK 大场景内存**：50k+ 粒子时需网格化/实例化；阶段四 Ray 并行时按需降采样显示。
3. **无 GPU 环境**：当前机器 VTK 可能走软渲染；真实验证需在目标部署机（有 GPU）复测。
